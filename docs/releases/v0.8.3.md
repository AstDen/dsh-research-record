# 0.8.3 — the guard reads where a command actually writes

0.8.2 documented its `bash` classifier as "a token scan, not a shell parser" and
left it there. Probing the real classifier afterwards found two writes it never
saw; both are fixed here, and both have a case in `smoke-regress.mjs`.

## Install

The package is not on npm yet. Install it from the repository:

```
git clone https://github.com/AstDen/dsh-research-record.git
dsh plugin --profile web add /path/to/dsh-research-record
```

or, pinned to a commit:

```
dsh plugin --profile web add 'github:AstDen/dsh-research-record#<sha>'
```

`dsh` >= 0.2.0, Node >= 22, Python 3 with `matplotlib` and `numpy` for the
figure helpers. No runtime dependencies.

## What changes for you

**A write after `cd` is checked where it lands.** `cd data && rm raw.csv` used to
report `raw.csv` at the workspace root — an innocent path — and the protected
`data/raw.csv` was written. The classifier now walks the command in segments and
resolves a relative destination against the directory the `cd` selected. An
absolute `cd` keeps an absolute candidate; a `cd` that leaves the workspace stops
the guess rather than inventing a path.

**A script from a heredoc asks instead of passing.** `python3 - <<'PY' … PY` used
to be invisible: the body is data to a token scanner, so the command read as a
bare `python3` and passed. It is now a question — "Allow a script from a heredoc?
The guard cannot see which files it writes" — with the delimiter in the audit
log. Like the destructive-command check, the question is tied to
`destructiveConfirm`, which is on by default. A heredoc into a file (`cat > derived/notes.md <<'EOF'`) stays silent: its
destination is already checked like any other redirect.

**Identifiers are monotone within a millisecond.** `ulid()` now increments its
random tail when called twice in the same millisecond, so two records created
together compare in creation order. The search tie-break uses the identifier when
`createdAt` matches, which means the older record could previously come first
about half the time.

## Upgrading

Nothing to change in a project: `.dsh/policy.json` format is untouched. After
reinstalling the package, restart the host DSH process so the new guard is the
one loaded — a running host keeps the module it booted with.

## Known limits

Still a token scan: a path built from a variable, a subshell, a second script or
an interpreter's own code can slip through, and a command whose *text* mentions a
protected path can be refused as a write. That trade is deliberate and it is
written down in the README's "Honest limits"; the real boundary is the
filesystem's own permissions.
